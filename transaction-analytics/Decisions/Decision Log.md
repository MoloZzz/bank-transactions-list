# Decision Log

Ключові рішення й чому. Формат: рішення → причина / наслідок.

## Архітектура й модель
- **Однокористувацький застосунок, без `userId`.** Це особистий інструмент, не платформа.
  Дедуп — `UNIQUE(source, externalId)`. → [[Invariants]] #4
- **`amount` = `numeric(38,0)` ↔ `BigInt`** (не `bigint`, не float). Крипта з 18 знаками
  (wei) переповнює `bigint` (макс ~9.2·10¹⁸); `numeric(38,0)` — безпечно, спільний тип для
  фіату й крипти. → [[Invariants]] #1
- **`decimals` (scale) зберігаємо поруч із сумою.** Ціле в мінорних одиницях не
  самодостатнє (UAH=2, JPY=0, BTC=8, ETH=18) — інакше показ вгадує scale.
- **Плоский enum `type`; P2P-ознака в `metadata`.** Простота за замовчуванням; окремий
  `p2p_buy` не заводимо. (підтверджено користувачем)
- **CSV `externalId` = детермінований хеш рядка.** CSV не має стабільного id; хеш
  стабільних полів + `UNIQUE(source, externalId)` дає ідемпотентність.
- **Крипто-трейд = одна нога активу + `tradeRef` у metadata.** Не будуємо FIFO/lot-tracking
  зараз, але й не унеможливлюємо. → [[Card↔Crypto Matching]]
- **Рахунок — окрема таблиця `accounts` + FK** (не просто текстовий `accountRef`). Треба
  показувати «картка ••1234 / UAH», групувати й фільтрувати. Міграція бекфілить existing
  із `metadata.accountId`. → [[Data Model]]

## Джерела / синк
- **Живі креди через `.env`; бекфіл — уся історія** (вибір користувача). Секрети не в код/Git.
- **Monobank: newest-first + stop на 400.** 400 = діапазон до існування рахунку → межа
  історії; так «вся історія» без падіння й без дати відкриття. → [[Monobank]]
- **Вікна з overlap на граничну секунду** (замість 1-сек діри) — жодна транзакція не
  випадає, дублі знімає дедуп.
- **Інкрементальний синк від watermark** (`max(bookedAt)` по source). Щоденний прогін
  тягне лише нове замість годинного бекфілу щоразу. Контракт лишився тонким:
  `fetch(sinceSec?)`, watermark рахує sync-шар. → [[Sync Engine]]
- **`currencyCode` = валюта РАХУНКУ, не операції.** `item.amount` — у валюті рахунку, а
  `item.currencyCode` — валюта операції; маркувати сумою операції = хибний ярлик на
  крос-валюті. Операційна сума/валюта → в `metadata`. Existing рядки чиняться SQL-
  пропагацією з `accounts` (amount був коректний, ламався лише ярлик). → [[Monobank]]
- **Crypto CSV = два окремих провайдери, не один із детектом формату.** `binance_p2p_csv`
  і `binance_deposit_csv` — різні `source`, різні файли, різні env-шляхи
  (`BINANCE_P2P_CSV_PATH`/`BINANCE_DEPOSIT_CSV_PATH`). Простіше й прозоріше за
  автовизначення формату за вмістом файлу. → [[Crypto CSV]]
- **P2P-ордер → один рядок (лише крипто-нога), fiat — тільки в `metadata`.** Не заводимо
  другий («fiat») рядок під P2P-ордер: fiat-сторона не є рухом по жодному з наших
  джерел-акаунтів (готівка/інший банк поза скоупом), і `TransactionType` не має fiat-руху
  без account-контексту. Курс/fiat-сума йдуть у `metadata` (`fiatAmountMinor` як рядок
  мінорних одиниць, не BigInt/float — jsonb не тримає BigInt) для кроку 5.
  `metadata.tradeRef` = order number (самопосилання, гак на майбутнє групування).
  → [[Crypto CSV]], [[Card↔Crypto Matching]]
- **`externalId` для CSV — завжди хеш через `buildExternalId`, навіть коли є нативний id.**
  Order Number і TXID стабільні, але хешуємо однаково для єдиної схеми externalId по всіх
  CSV-провайдерах і стійкості до майбутньої зміни формату колонок. → [[Providers]]
- **Крипто-scale — таблиця припущень у коді (`providers/binance/asset.ts`), не з CSV.**
  Binance CSV не містить canonical decimals активу. Таблиця (`USDT`/`USDC`=6, `BTC`=8,
  `ETH`/`BUSD`=18, фолбек 8) — задокументоване припущення; CSV-числа з надлишковими
  нульовими знаками (`320.00000000`) обрізаються рядково (`trimTrailingZeroFraction`)
  **перед** `parseDecimalToMinor` — float жодного разу не з'являється, реальна втрата
  точності (не-нульові цифри понад `decimals`) все одно кидає виняток. → [[Crypto CSV]]
- **CSV-крипто-рядки не мають `account`.** Немає концепції «картка» для Binance CSV;
  `accountId` лишається `null` (уже дозволено [[Data Model]] для деяких CSV-джерел).

## Метчинг card↔crypto (крок 5)
- **1-до-1 по картці, winner = мін |Δсума|, далі мін |Δчас|.** Один картковий дебет
  фінансує максимум одну крипто-покупку; серед валідних кандидатів найкращий обирається
  детерміновано, без залежності від порядку кандидатів. → [[Card↔Crypto Matching]]
- **Картковий дебет мусить передувати крипто-припливу в межах вікна** (`bookedAt ∈
  [cryptoTime − window, cryptoTime]`), не навпаки й не поза вікном. P2P: гроші йдуть з
  картки продавцю → крипта приходить пізніше.
- **`tolerance` за замовчуванням 0 (точний збіг сум)**, `window` за замовчуванням 7200с
  (2 год). Обидва — з env (`MATCH_TOLERANCE_MINOR`, `MATCH_WINDOW_SEC`; канон значень —
  [[Card↔Crypto Matching]]), не хардкод, щоб
  підлаштувати під реальні патерни без релізу коду.
- **`chooseCardMatch` — чиста функція (без БД, без I/O).** Уся логіка вибору
  ізольована від персистенції, щоб unit-тестувати вікно/суму/tie-break без Postgres.
  `MatchingService` — тонкий I/O-шар навколо неї (вибірка кандидатів, апсерт, 1-до-1).
- **Метчинг — окремий `npm run match`, не частина `sync`.** Пост-обробка запускається
  після того, як обидва джерела (Monobank + Binance P2P CSV) уже в БД; провайдери й
  `SyncService` про метчинг не знають. → [[Invariants]] #5
- **Апсерт по `cryptoTxId` (`UNIQUE`) з умовним `WHERE "manualOverride" = false` у
  `ON CONFLICT ... DO UPDATE`.** Повторний прогін ідемпотентний, але рядок, який
  користувач уже вручну підтвердив/переприв'язав, повторний матч ніколи не чіпає —
  умова живе в самому SQL (не в JS-перевірці перед записом), без вікна гонки.
- **Дебет, уже прив'язаний до "своєї ж" (не-override) покупки, тимчасово звільнюється
  в пул кандидатів перед перерахунком цієї ноги.** Інакше алгоритм бачив би власний
  попередній вибір як "зайнятий" і ніколи б не переобрав той самий дебет — ламало б
  ідемпотентність. Дебети, зайняті ІНШИМИ вже розрахованими покупками або
  `manualOverride`-рядками, лишаються заблокованими.

## Інфраструктура
- **Єдиний `DATABASE_URL`** замість набору `DB_HOST/PORT/...` (вибір користувача).
- **TypeORM 1.0, PostgreSQL 16.** `gen_random_uuid()` з ядра — без `pgcrypto`/`uuid-ossp`
  у міграції.
- **Sheets — батч-append на `flush()`**, не per-event: повний бекфіл = тисячі подій.
  → [[Events & Export]]
- **Google-клієнт через `google-auth-library` + Sheets REST**, легше за повний `googleapis`.
- **`process.exitCode` замість `process.exit()`** в entrypoint — прибирає libuv-assert на
  Windows при завершенні з відкритими хендлами.

## Процес / база знань
- **Vault-sync примусово через git pre-commit** (`.githooks/pre-commit`, `core.hooksPath`):
  коміт `backend/src|test` без зміни в `transaction-analytics/` блокується; обхід —
  `SKIP_VAULT_CHECK=1` лише для zero-knowledge правок. Хук також блокує дублювання
  статусу в `00 — Index.md` — єдине джерело правди про статус: [[Roadmap & Status]].
- **`build` пише, `check` — ніколи.** Хук викликає лише `check`, тож регенерація не може забруднити дерево, яке валідує (контракт як у `prettier --check` vs `--write`).
- **`_gen/*` — не `.md`.** Obsidian індексує лише `.md`; згенерована нота з `[[лінками]]` назавжди обнулила б виявлення сиріт. Тому `.txt`/`.tsv`/`.json`.
- **Свіжість нот — контент-дайджест `rev:`, не git-таймстемп.** Хук змушує код і vault лежати в одному коміті, тому `note_ts >= code_ts` — тавтологія; порівнюємо хеш файлів із `code:`.
- **`rev-stale` = `error`, не `warn`.** На `warn` правило інертне: попередження ніхто не читає. Зміна коду під `code:` блокує коміт, доки ноту не переглянуто й не перепінено (`vault pin`). Обхід — `SKIP_VAULT_CHECK=1`.
- **Ретрив-лог і `_retrieval.tsv`-baseline — поза `_gen/`.** Лог мутує на кожен `find`; у `_gen/`, який звіряється на свіжість, він робив би `check` нестабільним. Лог — у `.gitignore`, це локальне спостереження, не стан репозиторію.
- **`code-map.txt` — окремий артефакт, не частина `context.txt`.** Він завбільшки з увесь L1-пак і потрібен лише перед правкою `backend/src`, тож читається на вимогу.
- **L1 інжектиться хуками Claude Code** (`SessionStart`/`SubagentStart` у `.claude/settings.json`), а не покладається на память агента. `PostToolUse` на `Read` фіксує повні читання нот — це єдиний спосіб виміряти ескалацію L3→L4, з CLI її не видно.
- **`CLAUDE.md` — англійською, назви нот і `[[лінки]]` — ні.** Файл у контексті кожного запиту, а кирилиця коштує ~2× токенів на символ; але назви — це адреси для `find`/`show`/`Read`, перекладена адреса не резолвиться.
- **Контекстний бюджет — 50k на сесію, вимірюється `vault ctx`.** Профіль реальної сесії на 282k: `CLAUDE.md` + L1-пак разом дали <1% контексту, а 22% — ін’єкції харнесу, яких ніхто не друкував. Ретрив був не тим вузьким місцем; дорога сама робота. Тому канон переїхав із «менше читати ноти» на «один крок Roadmap на сесію, vault як хендовер».
- **`code-map.txt` покриває і `tools/vault`, не лише `backend/src`.** Профіль показав ~15k токенів (53% усієї вартості `Read`) на повне читання самого інструментарію — індексатор не індексував себе. Окремий scope у `MAP_SCOPES` дешевший за будь-яку дисципліну «не грепати».
- **Звіт сабагента — ≤30 рядків, refs а не тіла.** Правило «передавай refs, не тіла нот» діяло лише на вхід; вимір показав, що витрата — на виході (6 сабагентів, у середньому 6.6k, максимум 12.3k токенів звіту). Звіт, дорожчий за делегування, скасовує сенс делегування.
- **Ін’єкції харнесу рахуються окремо від роботи агента.** `task_reminder` виявився найбільшим окремим уникним рядком (23k токенів за 31 ін’єкцію — щоразу перевставляється ВЕСЬ список задач), а лістинги інструментів/агентів/скілів — фіксований оверхед. Тому закриті задачі видаляються, а тривкий статус живе в [[Roadmap & Status]], не в списку задач.
- **`vault ctx` читає транскрипти поза репозиторієм (`~/.claude/projects`), лише на читання.** Профіль потребує даних, яких у репо немає; команда нічого не пише і ніколи не викликається з хука — не через контракт `check`, а тому що її вартість росте з розміром транскрипту. Токени — оцінка за евристикою символів (±15%), не справжній токенайзер: співвідношення рядків достовірні, абсолютні числа — ні.
- **Контекст-губернатор — edge-triggered, не level-triggered.** Попередження про бюджет виводиться один раз на кожен перетнутий поріг (60/100/150%), а не щоразу: нагадування, що повторюється щохода, — це саме той дефект (task_reminder, 23k токенів за 31 ін'єкцію), який governor і мав виявити → [[Roadmap & Status]]
- **Хуки governor'а завжди fail-open.** Пошкоджений стан, недоступний транскрипт, битий JSON → повертаємо "дозволено, мовчки" і exit 0. PreToolUse стоїть перед кожним Read і Write, тому хук, що падає або блокує, гірший за відсутній хук
- **Гейти вмикаються на tier 2 (100% бюджету), а не завжди.** Write поверх наявного файлу і повний Read нотатки блокуються лише коли сесія вже за межами бюджету; до того — тиша. Втеча названа в самій відмові (Edit; `show` перед Read), плюс VAULT_CTX_OFF=1. Read нотатки дозволяється, якщо `show` по ній був за останні 15 хв — це легітимна ескалація L3→L4 для редагування, і агент ніколи не опиняється в пастці
- **Субагентам контракт звіту дається на старті, а не блокуванням на фініші.** SubagentStop з decision:block «не дає субагенту зупинитись; він продовжує працювати» — це дозволяє ще більше tool calls, а не коротший звіт. Тому ліміт ≤30 рядків інжектиться в SubagentStart (безкоштовно, бо хук уже є), а вимірює його наявний findings() → [[Roadmap & Status]]
- **BUDGET живе в guard.mjs, не в ctx.mjs.** guard завантажується перед кожним Read і Write, тому він не має тягнути за собою профайлер; залежність іде reporter → governor і ніколи назад. Сирі байти U+0000 у code.mjs і fs.mjs замінено на escape `\0`: ripgrep вважав ці файли бінарними, тож Grep не працював, а агент читав їх цілком
- **PreCompact скидає peak, а не лише рахує компакції.** Компакція — єдина подія, після якої записаний максимум перестає описувати живе вікно: воно реально зменшилось. Без ребейзу одна сесія на 280k тримала б гейти зведеними до самого кінця, скільки б місця компакція не звільнила; лічильник компакцій лишається як запис факту
- Продуктові пріоритети міряються, а не декларуються: `_metrics.tsv` (реєстр) + `vault evidence` (раннер) рахують метрики по живій БД. Тригер спрацював => працюємо над планом. Навмисно поза `check`: читає живі дані, тому не в git-хуці; вивід у gitignored `tools/vault/.evidence.tsv`, бо він змінюється разом з даними, а не з репозиторієм. Приватність — дві перевірки (whitelist колонок value//n + value мусить бути скінченним числом; саме друга ловить aliased текст). Plan 00 свідомо без метрики: імпорт грошей, яких БД не бачила, не вимірюється запитом до цієї ж БД.
